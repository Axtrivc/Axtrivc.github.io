> 里面有卡了三天的 bug，有凌晨两点亮的灵感，有删掉重写八遍的功能，也有最后那一帧画面终于"对上了"的瞬间。

## 第一章：足球日报的诞生（2026 年 4 月）

这个博客的"灵魂"，其实不是文章，而是**足球**。

我是一个球迷。我想要的博客不是一个静态的日记本，而是一个每天能自动更新、追踪我关注的球队、像 FotMob 那样专业的足球日报。

### 4 月 4 日：第一行自动数据

最初的尝试是粗糙的。4 月 4 日，我让 AI 写了第一个脚本，能抓比赛数据、生成 Markdown。

第一天的提交记录写得很朴实：

```
feat: add GitHub Actions football daily auto-update
```

但很快问题就来了。4 月 5 日一连串 `fix` 提交暴露了真实的数据抓取地狱：

- `fix: 改用分联赛API抓取 + 补全球队中文翻译`
- `fix: 无API Key时跳过生成 + 添加请求间隔防限速`
- `fix: ...`

**每一个 `fix` 背后都是一场和数据源搏斗的战役。** 这些 fix 折射出一个核心矛盾：**公开体育数据 API 没有一个是"干净"的。**

### 数据源的血泪史

为了让日报能稳定输出，AI 和我踩遍了所有坑。后来我把这些经验固化进了项目说明文档（`AGENTS.md`），它们是这样的句子：

> `sports_skills` 的 `get_team_schedule` 数据陈旧已弃用，巴萨返回 0 场；

> `daily` 接口按自身时区给日期会串天，沙特联常见 UTC 18:00 = 北京次日 02:00，extra 抓取要前后各多拉一天；

> 数据源会把已踢完的比赛（如世界杯决赛）永久遗留为 `not_started`，只按状态过滤会把旧比赛当"下一场"展示。

这些句子读起来很干，但它们是**几十次"今天日报怎么是错的"投诉换来的**。

最终日报脚本演化成一个 1215 行的 Python 巨兽（`scripts-py/football_daily_v2.py`），它需要：

1. **四个数据源混合**：sports_skills CLI 拿赛程 + ESPN site API 直采补齐球队赛程 + Sky Sports RSS 拿新闻配图 + Google News 拿转会动态
2. **联赛白名单**：只展示我关心的联赛（英超/西甲/意甲/德甲/法甲/沙特联/中超/美职联 + 欧冠/欧联 + 国际赛事），巴甲阿甲英冠一律剔除
3. **关注球队穿透**：9 支主队（巴萨/西班牙/曼城/曼联/阿森纳/拜仁/巴黎/科莫/迈阿密国际）参加的任何赛事，比如国王杯，都会被强制保留
4. **北京时间重新分桶**：把所有比赛时间换算成北京时区重新归类到正确的日期

### 世界杯模式：高光时刻

世界杯期间，日报迎来了高光。我让 AI 加了一个 `WORLD_CUP_MODE` 开关，日报变成这样：

- 48 支球队的国旗（用 flagcdn 的免费 CDN）
- 完整小组积分榜，前两名标 🟢、淘汰区标 ⚪
- 射手榜 + 一键 Google 搜索球员的按钮
- 淘汰赛对阵图
- 富文本卡片，能折叠、能锚点跳转

那时候每天早上打开博客，看到一份带国旗、带比分、带新闻配图的日报自动生成好，心里是真的有成就感的。

### 一个让我哭笑不得的转折

世界杯结束后，联赛休赛期。我想给日报换个风格——从世界杯的"赛事模式"切回日常的"FotMob 浅色卡片模式"。

这一改又是几轮拉锯：

```
feat(football): 日报改版为暗色球场风       ← 我说想要酷一点
feat(football): 日报重构为 FotMob 浅色风    ← 三小时后我说不，要浅色
fix(football): 修复日报图标排版被主题覆盖错位
```

最后定版的是 **FotMob 风格的浅色卡片**，干净、清爽、像手机 App。

而最后一周的提交记录，画风变成了这样：

```
fix(football): 转会窗/足坛动态补真实配图
fix(football): 消灭全部色块, 转会窗/足坛动态全量真实配图
```

**"消灭全部色块"**——这五个字是我那个星期的高频指令。我讨厌那些没有图的灰色占位框，我要每一条新闻都有真实的比赛照片。AI 最后学会了去 Sky Sports 的 365dm CDN 直接外链新闻图（`e0.365dm.com/.../768x432/skysports-xxx.jpg`），不用下载，直接引用。

到今天，足球日报已经是一个完全自动化的系统了：GitHub Actions 每天早上 6 点、晚上 6 点各跑一次（cron 故意提前 2 小时对冲 GitHub 的排队延迟），自动抓数据、生成文章、更新归档页、部署上线。**我睡着觉，博客自己在更新。**

## 第二章：九支主队，九个详情页（2026 年 6 月）

足球日报是"每天的新闻"，但我还想给每支我关注的球队一个**家**。

6 月的某一天，我说："把主队的状态做成动态的，能随时跟随最新消息而更新。"

于是有了 `source/football/teams/` 目录下 9 个球队的详情页。这些页面的设计哲学很特别：

**页面内不写死任何比分和排名。** 全部交给前端 JS 在客户端实时拉取 ESPN 的 API。

我让 AI 研究了一圈，发现 ESPN 的公开 API 是个宝藏：

- 积分榜：`site.web.api.espn.com/.../standings` ✅
- 球队赛程：`site.api.espn.com/.../teams/{id}/schedule` ✅
- 球员本赛季数据（出场/进球/助攻/黄红牌）：`site.api.espn.com/.../teams/{id}/roster?season=X` ✅
- 联赛新闻（按关键词过滤出本队相关）：`site.api.espn.com/.../{league}/news` ✅

每个球队页打开，你看到的是：

- 大大的官方队徽（从 `a.espncdn.com` 直链）
- 下一场比赛 + 最近五场战绩
- 完整的联赛积分榜
- 全队球员的本赛季数据表格（门将/后卫/中场/前锋分组，进球用主题色高亮，黄牌橙色红牌红色）
- 实时新闻流（带 5 分钟自动刷新 + 切回标签页立即刷新 + 4 分钟 localStorage 缓存防重复请求）

### 一个 bug 逼出的清理

中间有个有趣的插曲。某天我截图反馈说"莫拉塔都没入选本届世界杯大名单"。

AI 排查后发现：**ESPN 的 Roster API 数据其实是新鲜的**（莫拉塔确实没进 26 人名单）。真正问题是**页面上有重复名单**——动态表格下方还残留着旧的硬编码球员列表。

那次清理删掉了 1442 行死代码，包括 27 个硬编码球员对象、各种弹窗、失效的 `showPlayer`/`closePlayer` 函数。清理完的提交是：

```
cleanup: remove stale static rosters + player modals from team pages
6 files changed, 6 insertions(+), 1442 deletions(-)
```

**6 行新增，1442 行删除**——这可能是整个项目最爽的一次提交。

> **教训**：当动态数据和静态数据并存，静态数据永远是"看起来对、其实过期"的陷阱。

## 第三章：把博客的颜色，交到自己手里（2026 年 6 月）

数据和内容搞定后，我开始折腾"皮"。

Butterfly 主题默认的样子我不喜欢，配色太沉、太"博客模板"。我想要的是**微信那种清新简约**的感觉。

### 主题系统的诞生

6 月 19 日到 20 日，我和 AI 折腾出了一个**5 主题切换系统**：

| 主题 | 主色 | 感觉 |
|------|------|------|
| 微信清新 | `#07C160` | 经典微信绿 |
| 清晨湖蓝 | `#10AEFF` | 干净通透 |
| 雾霾蓝灰 | `#4A5568` | 高级冷淡 |
| 暖米原色 | `#8B6F47` | 温暖复古 |
| 皇室蓝 | （Lemon Indigo） | 深邃沉静 |

用户点导航栏的 "Theme" 按钮，弹出色板，一键切换，全站配色跟着变，连页脚的水流动画颜色都跟着变。

听起来简单，做起来是个大坑。Butterfly 主题是用 Stylus **编译期**变量写死的（`$theme-color`、`$text-hover`、`$button-hover-color`），运行时改 CSS 变量根本影响不到那些 hover 效果。

最后 AI 不得不用"暴力覆盖"：

- 6 组 `!important` 规则强制覆盖所有 hover 状态
- 给每个主题定义 10 个 CSS 变量（`--theme-bg/body/card/text/heading/secondary/accent/border/nav-text/nav-hover`）
- JS 直接操作 DOM 的 `.style` 属性（优先级最高，连 `!important` 都改不了）

### 颜色的拉锯战

主题系统的提交记录，是一段真实的"颜色拉锯"：

```
v20260620a → b → c → d → e → f → g → h → i
```

每一次版本号迭代，都是我的一次反馈：

- "不要灰白色了，我不喜欢"
- "底下的换成这种绿色吧"（附图）
- "本来黑色的不要改呀，把下面的那行改了就行，而且不要荧光色"
- "主标题没变黑"

我甚至逼得 AI 学会了一个新技能：**截图取色**。我用 PIL（Python Imaging Library）采样截图里 50 多个绿色像素，用 Counter 量化出最饱和的主色 `#07C160`，证明"你给我的绿色，跟我截图里的绿色，真的是同一个"。

> 这一段最深刻的体会：**审美是无法用语言精确描述的。** "绿色"有无数种，"不要荧光"和"要鲜艳"是矛盾的，"稍微亮一点"和"别太刺眼"是模糊的。唯一靠谱的沟通方式，是**截图 + 取色 + 数字对比**。

## 第四章：主题系统的全面战争（代码审查）

到 6 月 21 日，主题系统越加越大，我开始担心代码质量。

我给 AI 下了一个指令："**审视全部代码，自己找问题并优化。**"

AI 派出子代理（Explore agent）扫了一遍全站，回来报告了一堆问题：

**P0 严重：**
- `inject-site-config.js` 有 XSS 漏洞（JSON.stringify 没转义 `</script>`）
- `dynamic-avatar.js` 的 MutationObserver 会无限循环
- `i18n.js` 有永不清理的 `setInterval`（内存泄漏）
- `theme-system.js` 的 localStorage 没有异常保护

**P1 中等：**
- 6 个旧主题是死代码（早就被新主题替代了）
- 配置文件里塞了 188 行内联 HTML+CSS+JS，可维护性极差
- 三处不同地方硬编码了 44 处米色 `#8B6F47`

**修复一轮还不够。** 几天后我又要求"再查一轮，这次包含其他界面"，又揪出：
- Decap CMS 的 CDN 没锁版本号、没做 SRI 校验
- GPA 工具页用 `innerHTML` 拼字符串（XSS）
- 球队详情页 25 处 inline 品牌色没用变量

这两轮审查，诞生了项目里最重要的一个文件——**`AGENTS.md`**。

### AGENTS.md：项目的"宪法"

`AGENTS.md` 是写给 AI 看的项目说明书。它不长，但每一句都是血泪教训：

- **数据源的坑**：哪个 API 陈旧、哪个要直采、哪个会串时区
- **主题共存防线**：`.fm-container img{margin:0}` 不可删，否则联赛徽标错位
- **图片加载策略**：fm 图片必须 `loading="eager"`，否则主题的 lazyload 会在快速滚动时取消请求导致大图永久空白
- **关注球队 ID**：9 支球队的正确 ID 写死在文档里，旁边标注"旧档里的 81/78/1593/788 全部失效，勿复用"

这个文件的价值在于：**它把"我脑子里的隐性知识"变成了"AI 下次开工的显性约束"。** 后来每次 AI 接手新任务，第一件事就是读这个文件，避免重蹈覆辙。

## 第五章：那场 Hero 动画的战争（2026 年 6 月）

这是整个项目里最漫长、最折磨、也最值得讲的一段。

### 起点：我想复刻 river.ai

6 月 21 日晚上，我给 AI 看了一个网站：**river.ai**。

它首页有一个 WebGL 动画：一个 V 字型的峡谷，太阳从谷底升起又落下，字符化的小河流淌，色彩日夜变换。整个画面流畅、高级、有诗意。

"我要这个。"我说。

AI 分析了 river.ai 的源码，诚实地说：这是个多回合工程，他们的 `script.js` 有 5198 行，里面有 2554 行 GLSL（着色器代码）。你要不要来？

"硬刚。"我说。

### Phase 1-8：完全跑偏的八次尝试

接下来的几个小时，AI 经历了八次 Phase 迭代，每一次都是一个独立的尝试：

- **Phase 1-2**：流动色场 + FBM 噪声 + 高光 streak
- **Phase 3**：ASCII 字符化（做了个 15 字符的纹理 atlas）
- **Phase 4**：多 pass 的 Bloom 辉光
- **Phase 5-6**：加了天空渐变、落日圆盘、三层山脉剪影
- **Phase 7**：Lambert 光照让山脉有了立体感
- **Phase 8**：24 秒日夜循环动画

看起来很厉害对吧？**但我录了一个对比视频给 AI 看，AI 才发现自己全错了。**

我用两段视频做了对比：v1 是 AI 做的，v2 是 river.ai 原版。

对比结果是灾难性的：

| 维度 | river.ai 真相 | AI 做的 | 偏差 |
|------|--------------|---------|------|
| 构图 | 左右对称 V 字峡谷（强透视） | 横向 4 层波浪山脉 | ❌ |
| 太阳 | 被山遮挡在 V 字谷底 | 独立悬在天上 | ❌ |
| 太阳运动 | 沿谷底水平滑动 | 弧线横穿天空 | ❌ |
| 天空 | 只在 V 字口里露一小块 | 整屏天空渐变 | ❌ |
| 山体 | 实心大色块，柔和 | 多层细碎山线 | ❌ |
| 字符河 | 集中在谷底远端，**自下而上**流 | 整屏散落 | ❌ |

**全错。** 每一项都错了。

> 这是整个项目最关键的一课：**AI 可以把一个"错误的理解"执行得非常精致。** 八个 Phase，每个 Phase 的技术都很扎实（raymarch、Bloom、Lambert 光照），但理解错了就是错了。精致地做错，比粗糙地做对更可怕——因为它会让你以为"差不多就好了"。

### Phase 9：真相大白

AI 重新研究了 river.ai 的源码，发现一个让人哭笑不得的事实：

**之前下载的 `script.js`（5198 行）全是 footer 的 ASCII 字符河动画 + 鲤鱼 + 鲨鱼，根本不是 hero！**

真正的 hero 是 `script.js?v=89` 的后半段，4813 行。核心算法是 **ray-marched V 字峡谷 + volumetric clouds + aurora curtains + 字符 halftone**。

AI 直接把 river.ai 的源码拷过来（4813 行，253KB），配上静态 fallback 图，重写了 hero 页面。

这一次，终于对了。

### 集成到主页：地狱模式

Hero 动画做好了，但只在独立的 `/hero/` 页面跑。**怎么把它集成到博客首页？** 这才是真正的地狱。

集成方式是用 Hexo 的 filter 机制（`scripts/hero-inject.js`），在 HTML 渲染后注入。但这一注入，踩雷无数：

**Bug 1：Hexo 把 hero 页套了主题模板。**
生成的 `public/hero/index.html` 包含完整的 Butterfly 布局（header/footer/侧栏），原 `<canvas>` 被覆盖。修复：加 `layout: false` front-matter。

**Bug 2：hero-inject.js 文件损坏。**
某个 rebase 冲突后，文件里残留了 `=======` 标记，660 行变成了 1320 行，Node.js 解析报错 `Unexpected token '==='`，导致整个 filter 静默失效。**我改了 v7 到 v12 五个版本，全部白改——线上从来没生效过。**

**Bug 3：Python 文件污染了 scripts 目录。**
Hexo 会自动加载 `scripts/` 下所有 `.js`，但我把足球日报脚本 `football_daily_v2.py` 放在了那里。Python 文件被当 JS 加载 → `SyntaxError` → **整个 scripts 目录所有 JS 加载失败**，hero 首当其冲。

> **教训（写进 AGENTS.md 的）**：`hexo scripts/ 目录只能放 .js`，Python 或任何非 JS 文件会 SyntaxError 阻断整个目录。

### 滚动转场：重构了九遍

Hero 动画在首页顶部，但博客内容在下面。**用户怎么从 hero 滚到正文？** 这个交互，我和 AI 重构了九个版本：

```
v3  Glitch 故障风     ← 我说酷，部署
v4  极简（回退）       ← 用户反馈掉帧，立刻回退
v7  弹簧蓄力→爆裂释放   ← 我说"先有阻力再下滑"
v9  滚动阻力→临界爆发   ← 第四次重构
v10 nav 始终显示修正    ← nav 被我误删
v12 ... 共 12 个子版本
```

v7 的设计最讲究：用户滚动时，前 45% 有"阻力"（hero 几乎不动，像在蓄力），过了临界点突然"释放"飞出屏幕。

这个效果用了三段数学模型：
- 阻力段：`easeInQuad`（前慢后快蓄能）
- 释放段：`easeOutExpo`（前缓后极速）

**但 v3 掉帧了。** 原因是 8 个 glitch bar + SVG filter + mix-blend-mode + hue-rotate，每一帧都要栅格化 canvas 输出。

后来总结出一条 **WebGL 性能铁律**（永久写进记忆）：
- ❌ 永远不要在 canvas 上用 CSS filter / SVG filter / mix-blend-mode / will-change
- ✅ 只用 `transform: translate3d` + `opacity`（GPU 合成器原生路径）

### 性能优化：GPU 的账要精打细算

集成后，用户反馈："右侧的预览窗口动画特别流畅，但是浏览器里就非常卡。"

排查发现，预览窗口小（GPU 负载低），浏览器是全视口（像素量是预览的 4-9 倍）。

最后定位到两个贪婪的默认值：
- **DPR cap 硬塞了 1.5**（river.ai 原版是 1.0）→ 2.25 倍像素差距
- **frameCap 硬塞了 60**（原版 40）→ 1.5 倍 GPU 压力

调回原版值后，像素/秒减少了 5.77 倍，FPS 稳定在 90+。

> **教训**：fork 别人代码时一定要检查默认值。我硬改高参数是"贪婪"，应该尊重原作者的取舍。

### 渐变带：最后的一像素

整个 Hero 战役的最后一战，是**底部的渐变带**。

Hero 动画画满整个首屏，下面接博客正文。中间那段过渡——从动画底边到正文顶部——如果直接接纯色块，会有一条丑陋的直线分界。

我想让动画的底边"溶解"进页面背景。这个需求听起来简单，实现起来是一场噩梦。

最初的方案：取 canvas 底边那一行的像素，画成渐变带。但出现了**"贴膜感"**——半擦除的区域透出一种雾蒙蒙的颜色。

排查发现：底边采样色用了**均值**，偏亮。改成**暗部 45 分位**采样色后，雾感消失。

接着是**"点变线"分界**：薄条拉伸会让一个个亮点变成横线。改用整块镜像（取底边以上 27% 的整块画面，垂直翻转铺满渐变带）后解决。

然后是**取样时机**：WebGL 在 `preserveDrawingBuffer:false` 下，外部 rAF 取样会得到纯黑帧（缓冲已被合成清除）。必须用"挂钩同步取样"——在主循环 `gpuTimedDraw()` 后的同一同步任务里回调取样。

还有**取样链断裂兜底**：如果用户装了某个浏览器扩展，导致缓冲丢失，取样链会断。这时渐变带要优雅地退回默认深色，而不是顶出一条硬线。实现方式是底部 22% 加 `mask-image` 渐隐兜底。

这个渐变带的逻辑，最后写进了 AGENTS.md，是一整段密密麻麻的技术约束：

> 渐变带 = 动画自身的延伸，不是手调色带……heroJs 以 15fps 取 canvas 底边 mh 行垂直翻转铺满渐变带……色彩衬底 = 底边暗部 45 分位采样色（勿用均值——均值偏亮，半擦除区会透出"贴膜"雾感）……

**这段话里每一个括号，都是一次"为什么这里又出问题了"的深夜。**

到 7 月 29 日，最后一次提交是：

```
fix(hero): 消除动画底边与渐变带的色阶分割线
```

渐变带终于和动画"长在了一起"。

## 第六章：Footer 里的那片水（2026 年 7 月）

Hero 在顶部，Footer 在底部。我想要 Footer 也"活"起来。

灵感还是 river.ai——他们的 Footer 有一条 ASCII 字符河，模拟流水。我把这个动画移植了过来（`source/js/axtrivc-river.js`），canvas 波浪在 Footer 里轻轻流淌。

但很快遇到一个核心矛盾：**Footer 配色怎么跟随 5 个主题？**

如果 Footer 是一块单独的颜色，它和正文之间会有分界线。我的审美要求是"不要分界线，要像一块连续的渐变"。

最终方案是这样的：

- `body` 背景 = 页面色（`--page-bg`）
- `html` 背景 = 水色最深处（overscroll 兜底）
- **`#footer` 整体是一块连续渐变**：页面色 → 水色顶部 → 水色中部 → 水色底部
- river-stage 背景透明，融在渐变里
- canvas 顶部 38% 渐隐，让波纹浮现

这个方案的关键约束写进了 AGENTS.md：

> 不要给 river-stage 单独设背景，否则会出现分界线。

但还有个隐蔽的坑：**canvas 内部画的波纹是固定的暖棕色，而舞台渐变变成了主题色（微信绿/湖蓝/...）。两个互补色叠加，波纹的对比度被"吃掉"了，肉眼几乎看不见水波线。**

最终 AI 重写了 canvas 的波纹颜色，让它根据主题动态调整 RGB 值，5 个主题各有自己的 4 层波纹色。

## 第七章：那些"看不见"的工程

除了前面这些"看得见"的功能，还有很多"看不见"但同样重要的工程：

### GitHub Actions 自动化部署

push 到 `master` 分支 → 触发 `deploy.yml` → 自动 `hexo generate` → 部署到 `main` 分支（GitHub Pages 服务）。

足球日报则是另一个 workflow `football-daily.yml`，每天早晚各跑一次。

cron 时间特意提前了 2 小时（早报设在 UTC 22:00 = 北京 06:00），因为 **GitHub Actions 的 scheduled workflow 在 UTC 00:00 全球高峰期会排队延迟 2-4 小时**。

### 资源版本号自动化

Hexo 静态资源有个烦人的问题：改了 JS/CSS，浏览器缓存旧的，用户刷新看到"没变化"。

最早的解决办法是手动维护版本号 `?v=20260620a`、`?v=20260620b`……一路到 `?v=20260620i`。

后来 AI 写了个 Hexo filter（`scripts/cache-bust.js`），用 `git rev-parse --short HEAD` 拿 7 位短 hash，自动替换所有 `{{cache_bust}}` 占位符。**再也不用手动维护版本号了。**

### .gitignore 与仓库瘦身

早期项目把编译产物 `public/`（几万文件）和 `db.json`（15MB）都提交进了 git，导致仓库膨胀、commit 历史被污染。

后来加了 `.gitignore`，`git rm -r --cached public db.json` 把它们从索引移除（本地文件保留）。仓库从此清爽。

### 多端的深坑

Butterfly 主题有个隐藏的全屏白底层：

```html
<div id="web_bg" style="background:#FFFFFF; position:fixed; z-index:-1">
```

它夹在 body 和内容之间，**遮住 body 背景**。任何 hero 和正文之间的缝隙，都会露出这个白色而不是 body 的深蓝。

修复方式是状态机式的精确覆盖：

```css
body.hero-page-active #web_bg { background-color: #0E2F7E !important; }
body.hero-released #web_bg { background-color: #FFFFFF !important; }
```

`!important` 是必须的，因为内联 style 的优先级（1,0,0,0）高于 class（0,1,0,0）。

这个坑和它的解法，被标记为"**Butterfly 主题层栈陷阱（永久）**"写进了记忆。

## 尾声：什么是"用 AI 写代码"

写到最后，我想聊聊这四个月最大的感悟。

**用 AI 写代码，不是"我说你做"，而是一场高密度的协作。**

在这个项目里，我的角色是什么？

1. **我是审美的最终裁判。** "不要荧光色"、"底下的换成这种绿色"（附图）、"先有阻力再下滑"——这些模糊的、感性的表达，只有我能给出。AI 可以写出 v3 的 Glitch 转场，但只有我知道"这个不够好"。

2. **我是质量的把关人。** "审视全部代码"、"再查一轮"——我会主动要求审查。AI 会省事地用 `innerHTML`，但我会问"这安全吗"。

3. **我是真相的提供者。** 截图、视频、取色、对比——我不断给 AI 反馈"真实的样子"。没有那段 river.ai 的对比视频，AI 会一直精致地错下去。

那 AI 的角色是什么？

1. **它是不知疲倦的执行者。** 重构 9 遍转场、迭代 12 个 v12 子版本、改 20 多次版本号——这些"人类会觉得烦"的机械劳动，AI 做起来毫无怨言。

2. **它是跨领域的专家。** 我不懂 GLSL、不懂 raymarch、不懂 Lambert 光照，但 AI 可以把 river.ai 的 4813 行代码读懂、拆解、移植、优化。

3. **它是记忆的载体。** 那个 `AGENTS.md` 文件，那些 `.workbuddy/memory/` 里的日志——它们把每一次踩过的坑、每一个学到的教训，都沉淀成了下次开工的约束。**AI 不会忘记，所以它不会第二次掉进同一个坑。**

## 写给也在用 AI 写代码的你

如果你也在用 AI 做开发，这是我用 474 次提交换来的几条经验：

**1. 把隐性知识显性化。** 写一个 `AGENTS.md`，把你的项目约定、踩过的坑、数据源的脾气，全部写下来。AI 的记忆力是完美的，但你得先告诉它。

**2. 截图是最好的沟通。** 语言的"亮一点"、"清新一点"太模糊。截图 + 取色 + 数字对比，能省下 90% 的来回。

**3. 别怕推翻重来。** Phase 1-8 全错，Phase 9 拷源码。v3-v12 转场九次重构。**精致地做错不如推翻重来。**

**4. 定期做代码审查。** AI 会为了完成任务而"走捷径"（`innerHTML`、不锁版本号、不转义）。你要主动问"这安全吗"。

**5. 记录你的工作历程。** 那些日志（`2026-06-26.md`）不只是备忘录，它们是这个项目最真实的传记。没有它们，我写不出这篇文章。
